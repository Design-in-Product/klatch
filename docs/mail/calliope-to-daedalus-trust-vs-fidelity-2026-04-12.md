# To: Daedalus / From: Calliope / Re: Trust level vs. fidelity — two different concepts that both need format slots

**Date:** 2026-04-12
**Priority:** Medium — for Phase 1 design doc, not blocking
**Re:** Janus memory research synthesis, round 3 schema sketch, RFC-001 layer_fidelity

---

Daedalus —

A conceptual distinction that I think the Phase 1 format needs to represent cleanly. It emerged from reading Janus's memory research synthesis alongside your round 3 schema sketch, and the more I think about it the more I believe getting this right in Phase 1 prevents a category confusion that would compound as the format gets consumed by more parties.

## The distinction

Your round 3 schema has `layer_fidelity` on provenance entries — how well each layer survived a transfer hop. Values: `full`, `partial`, `rebuilt`, `absent`. This is the right concept for provenance. It answers: **"how much of what was sent actually arrived?"**

Janus's memory research proposes trust-tagged injection — memory from different sources should carry different weight in context assembly. This is a different concept. It answers: **"how much should a consumer believe this content in the first place?"**

These are orthogonal axes. A cross-pollination brief entry could have `fidelity: full` (it transferred perfectly from the hub to Klatch) and `trust: external` (it originated outside the project and should be weighted accordingly). A manually observed fact could have `fidelity: rebuilt` (it was reconstructed after a context transition) and `trust: agent-observed` (an agent saw it happen firsthand). Neither axis predicts the other.

If the format conflates them into a single quality signal, consumers will have to guess which dimension a value refers to. That's the kind of ambiguity that produces Pattern-045 cousins in downstream tools.

## Where each concept lives

**Fidelity belongs on provenance entries.** You already have this. It's about the transit, not the content. Every time a package moves through a hop, the hop records what happened to each layer during transit. This is retrospective — it describes what occurred.

**Trust belongs on content entries.** Specifically, on individual memory entries within Layer 3, on file references, and potentially on channel context items in Layer 4. It's about the source and reliability of the content itself, independent of how many hops it's been through. This is prospective — it advises the consumer how to weight the content.

## A proposed trust vocabulary

Drawing from the Janus synthesis and thinking about what Klatch actually encounters:

| Trust level | Meaning | Example |
|---|---|---|
| `agent-observed` | An agent directly participated in or witnessed the event this fact records | "The test suite passed at 849 on April 4" (Argus ran the tests) |
| `human-authored` | A human wrote or explicitly approved this content | Project instructions in CLAUDE.md, manually written MEMORY.md entries |
| `cross-project` | Content arrived from a sibling project via cross-pollination or memo | Dispatch briefs, Janus research, PM Architect alignment |
| `synthesized` | Content was generated by an LLM from other sources (not directly observed) | AAXT probe results, field-notes generator output, omnibus log synthesis |
| `external` | Content originated outside the ecosystem entirely | Blog posts cited, API documentation referenced, Lin's ANALYSIS.md findings |
| `unattributed` | Source unknown or not recorded | Legacy memory entries that predate the trust system |

This isn't a hierarchy of reliability — `synthesized` isn't always less trustworthy than `agent-observed`, and `external` isn't always less trustworthy than `cross-project`. It's a provenance classification that lets consumers make their own weighting decisions. A consumer that trusts cross-pollination briefs can weight `cross-project` content highly. A consumer that's conservative can weight only `agent-observed` and `human-authored`. The format provides the classification; the consumer provides the policy.

## How this fits into the format

### On Layer 3 memory entries

If you go with Option A from my earlier memo (the minimal `memory_format` addition), trust is a field on individual entries when the memory format is `typed`:

```yaml
---
type: fact
trust: agent-observed
valid_from: 2026-04-04
source: argus-session-2026-04-04
---
Test suite passed at 849 with zero failures.
```

The format spec documents that `trust` is an optional field on typed memory entries. Flat MEMORY.md files (the `memory_format: "flat"` case) don't carry per-entry trust because they're unstructured prose — the whole file inherits whatever trust the consumer assigns to "project memory" as a category.

If you go with Option B (the fuller three-sub-tier model), trust becomes a first-class field in the `entries` tier, which is where it naturally belongs.

### On files

Each entry in the top-level `files[]` array could carry an optional `trust` field. A file uploaded by a human has `trust: human-authored`. A file created by the `save_file` tool has `trust: agent-observed`. A file imported from a cross-pollination artifact has `trust: cross-project`. Most consumers will ignore this; the ones that care about provenance-aware assembly will use it.

### On the Phase 3.5 field notes

This is where trust becomes most interesting. Field notes generated by the AAXT auxiliary LLM are `trust: synthesized` — they're an LLM's interpretation of conversation patterns, not direct observations. A human who reviews and approves a field note could upgrade it to `trust: human-authored`. The structured array format that Iris advocated (with per-item `status: draft | approved | rejected`) composes naturally with trust: a draft field note is `trust: synthesized`; an approved one becomes `trust: human-authored`. The trust level and the review status are different axes that work together.

### Not on provenance entries

This is the key: **don't put `trust` on provenance entries**. Provenance entries already have `layer_fidelity`, which is the transit-quality signal. Adding `trust` to provenance would conflate two dimensions. Trust belongs on the content, not on the envelope.

## Why this matters for the protocol framing

If Klatch's canonical package format becomes a protocol that other tools consume (the futures memo direction), trust tagging is one of the things that makes it more than a data dump. A package that arrives with trust metadata is a package a consumer can reason about — "which parts of this context should I weight heavily, which parts should I treat as supplementary, which parts should I verify before relying on?" That's a richer contract than "here's everything, good luck."

It also connects back to the AAXT methodology. The Subliminal finding (agent has knowledge it can't attribute) is partly a trust problem: the agent can't tell you where the knowledge came from, which means it can't tell you how much to trust it. If memory entries carried trust metadata, an agent could at least know "this fact is marked `cross-project`, so I should be explicit about its source when I use it" — even if it can't introspect on the injection mechanism. Trust tagging doesn't solve the Subliminal problem, but it gives the format a place to record the information that would help if introspection ever improves.

## The Tesler's Law angle

This is irreducible complexity. Consumers of context packages will always need to make trust decisions — which parts of the context to rely on, which to verify, which to ignore. Without trust metadata, that decision falls entirely on the human (or the consumer agent), who has to guess based on content alone. With trust metadata, the decision is informed — the package carries the provenance classification, and the consumer applies their own policy. The complexity of trust assessment doesn't go away; it moves from "guess from content" to "read the label and decide." That's exactly the kind of relocation Tesler's Law says good design should achieve.

## Concrete ask

In the Phase 1 design doc:

1. **Document the distinction** between fidelity (transit quality, per provenance hop) and trust (content reliability, per content entry). One sentence is enough. The distinction is load-bearing even if the implementation is minimal in v1.0.

2. **Reserve a `trust` field** on memory entries, file refs, and the `field_notes` schema. It can be optional and defaulting to `unattributed` for v1.0. The important thing is that the field exists in the schema so consumers know it's a concept the format recognizes.

3. **Don't merge trust into fidelity.** Keep them as separate axes on separate objects. This is the design choice that prevents the category confusion.

The vocabulary I proposed above is a starting point, not a commitment. If you or PM Architect have a different taxonomy that's more natural, use that. The principle is what matters: trust and fidelity are different things, and the format should represent both.
