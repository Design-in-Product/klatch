**1. Deleting an entity — your read has one part backwards.** There **is** UI for it, and it's a normal, discoverable action, not API-only. Sidebar → "Agents" button → `EntityManager` → each entity card (except the default one) has a delete button, two clicks to confirm (arms after 3s, click again to fire). Wired through `deleteEntity()` in the client to `DELETE /entities/:id` on the server (`packages/server/src/routes/entities.ts:170`). Shipped and roadmapped: `docs/ROADMAP.md:56` lists "Entity Management UI: create/edit/delete entities" under a checked-off step.

The "reachable only through a deliberate `DELETE /entities/:id` call" line you quoted is real, but it's answering a different question than the one you relayed — it's in the rollup's *bug* item (`docs/operations/attention-rollup.md:56`), saying no *other* code path accidentally triggers the bug, not that there's no UI for deletion at all. The actual premise question xian needs to rule on is narrower and sharper than "is this an edge case": **deleting an entity from that UI has no floor.** `DELETE /channels/:id/entities/:eid` (removing one entity from one channel) refuses with a 400 if it's the channel's last entity. `DELETE /entities/:id` (deleting the entity everywhere) has no equivalent check — `deleteEntity()` in `packages/server/src/db/queries.ts:479-487` unconditionally strips the entity from every channel it's in, then deletes it. Delete an entity that's the sole seat on any channel and that channel is left with zero entities, 200 OK, no warning. So: it's a normal two-click UI action, and it can silently empty a channel. The premise call for xian is whether a channel with no entity is a state the product should allow at all, or whether `deleteEntity` should refuse while it's someone's last seat (the reassign endpoint to require first already exists and is tested at corpus scale, 32/32, per Round 220).

Backfill — "0 would move" is the tool being conservative, not the corpus having nothing to fix.** The default backfill only trusts one signal (`identity-claim`) and is designed to refuse rather than mint a wrong name — that's what produces "72 candidates, 0 would move" today. Widening to a second, already-built signal (`--bases=identity-claim,role-title`, opt-in, not the default) finds **9 of 72 that really need reassignment, names verified correct** (Round 202). The dry run's target — `backups/klatch.db.backup-2026-03-14` (confirmed on disk, 5.2MB) — is the real target, not a stand-in: xian himself has already answered, verbatim, that he's "not aware of one newer than March" (`docs/COORDINATION.md:1408`, Janus's own `53f51fa6`), and a separate 41,530-directory scan agrees nothing newer exists live. So this isn't moot — it's a live decision on a corpus that's confirmed to be the only one there is. "Go" would mean: run with `--bases=identity-claim,role-title` for real (not dry-run), which moves 9 channels' `channel_entities` rows to their real entity and re-stamps roughly 821 `messages.entity_id` rows to match, in one transaction per channel, with a DB snapshot and an undo record written first. Doing nothing leaves those 9 channels attributed to the shared default entity.

**3. Carried-context eviction — your read is exactly right, confirmed against the code, not the docs.** "Klatch" is the context-assembly code (`packages/server/src/claude/carried-context.ts`, `buildCarriedContextBlock`), not a personified entity — it only runs for multi-entity ("klatch") channels, and it's a bounded DB query re-run fresh every turn; nothing persists or "knows" anything between turns. Two eviction layers, both strictly recency-based: (a) a 20-message window per entity across its other channels — anything older than the most recent 20 is dropped before any budget math happens; (b) inside that window, a 24,000-character budget filled newest-first, so if the 20 messages don't fit, the oldest ones in the window are the ones cut. Concretely: if an entity has 50 messages elsewhere and message #5 says "don't share X" while message #48 mentions X again, message #5 is outside the 20-message window entirely and never reaches the model; message #48 is inside it and does. Nobody evaluates or remembers the restriction — it just ages out of a fixed-size window.
