## 16:55 — Models API Verification (Calliope assignment #1)

**Question:** Is `GET /v1/models` ready for Daedalus to replace the hardcoded `AVAILABLE_MODELS` in `packages/shared/src/types.ts` with dynamic discovery?

**Answer: YES — the API is ready.**

### API Response Schema

`GET /v1/models` returns a `data` array where each model object includes:

| Field | Present | Notes |
|-------|---------|-------|
| `id` | Yes | Model identifier (e.g., `claude-opus-4-6`) |
| `display_name` | Yes | Human-readable (e.g., "Claude Opus 4.6") |
| `created_at` | Yes | ISO 8601 timestamp |
| `max_input_tokens` | Yes | Max input context |
| `max_tokens` | Yes | Max output tokens |
| `capabilities` | Yes | Rich nested object (see below) |

### Capabilities Object (per model)

The `capabilities` field is a structured object with sub-fields:
- `batch` — `{ supported: bool }`
- `citations` — `{ supported: bool }`
- `code_execution` — `{ supported: bool }`
- `context_management` — strategies: `clear_thinking_20251015`, `clear_tool_uses_20250919`, `compact_20260112`, each with `supported` flag
- `effort` — levels: `high`, `low`, `max`, `medium`, each with `supported` flag
- `image_input` — `{ supported: bool }`
- `pdf_input` — `{ supported: bool }`
- `structured_outputs` — `{ supported: bool }`
- `thinking` — `supported` flag + `types` with `adaptive` and `enabled` modes

### Klatch's Current Model List vs. API

Klatch currently hardcodes three models in `packages/shared/src/types.ts`:
- `claude-opus-4-6` — should be in API response
- `claude-sonnet-4-6` — should be in API response
- `claude-haiku-4-5-20251001` — should be in API response

The API uses versioned IDs (like `claude-opus-4-6`), consistent with what Klatch already uses. The response also includes `display_name` which could replace our hardcoded `label` field.

### Recommendation for Daedalus

**Green light.** The API provides everything Klatch needs:
1. Model IDs match our current convention
2. `display_name` can replace hardcoded labels
3. `max_tokens` and `max_input_tokens` are present (useful for the 64K/128K output limit feature)
4. `capabilities.effort` levels are enumerated (useful for per-entity effort parameter, #17)
5. `capabilities.thinking` modes are enumerated (useful for adaptive thinking config)

**Implementation notes:**
- The API returns ALL available models, not just the three we currently show. Daedalus should filter to supported models or let the user see the full list.
- Alias handling: unclear if aliases like `claude-sonnet-latest` appear in the response. Klatch's `MODEL_ALIASES` map may still be needed for legacy data migration.
- Consider caching the response (models don't change often) — no need to hit the API on every page load.
- The `capabilities` object could drive UI: e.g., only show "thinking" toggle for models where `capabilities.thinking.supported` is true.
