## 07:20 — Track 2 design work begins: object model conversation

xian asked whether a linear "let's design X" conversation across the Tier 3 items would work. I recommended object model first — surfaces are projections of the object model; muddled model produces muddled surfaces. Started `docs/ux/object-model.md` with candidate objects (7 categories) + 6 candidate tensions ranked by consequence.

### Tension 1 resolved: Channel / klatch / chat

Channel is parent (conceptual/implementation); chat = single-entity channel; klatch = multi-entity channel, the product's branded name for a group chat.

**Load-bearing insight (worth its own status as architectural truth):** Klatches are synthetic. Each agent in a klatch experiences a normal single-user chat with context about other agents injected. The human sees a group chat. The agents don't. This explains why the entity reframe works, why composition-from-existing-chats is the right gesture, what interaction modes really are (orchestration patterns), and the two-audiences-two-views nature of Klatch (Tesler's Law in both directions).

### Tension 2 resolved: Entity / role / conversation

- **Entity** = continuous single-agent conversation with a purpose (the broad unit)
- **Role** = subset of entity; entity that has accrued persistent identity, consistent name/title, ongoing function in a project
- **Role persistence is Klatch's unique value proposition** vs. generic chat products; lives on the layer stack (L5 + accumulated L3 + Phase 3.5 calibration)
- xian's canonical use case: roles-in-klatches. Other patterns allowed.

### Tension 3 resolved: What's in a project?

Project typically contains channels + L2 + L3 + KB files + roles.

**Principle (xian's framing):** Object definition shouldn't encode constraints that are typical-but-not-mandatory. A role typically belongs to a project (canonical); a role may not (allowed, not forbidden). The relationship is contingent.

**Consequence:** No cross-project roles in xian's workflow (Janus is bound to DinP, which happens to be a parent-of-projects). "Cross-project" is a project property, not a role property.

### Tension 4 tentatively resolved: L4 as object or property?

Candidate C: L4 stays a string (what the agents see); a separate structural object (workflow — see T6) lives alongside it (what the system orchestrates). Two audiences, two views. xian flagged as subtle, may refine with use.

### Tension 5 resolved: Where do field notes attach?

To the entity (which = the chat). Canonical case has one user, project-scoped role — so user and project are implicit. Data model permits qualification by project/user; doesn't require it.

### Tension 6 resolved: Workflow / meeting as first-class object?

- **Workflow** is the parent term
- **Meeting** is one type of workflow; "klatch" branding already suggests this
- **Every klatch has a workflow.** Not optional.
- **Default workflow is broadcast** — add roles, type a message, all receive it. Maps to panel mode. Simplest possible shape; klatches evolve from here.

xian raised expected-vs-actual question; my notes suggest a template-vs-execution distinction as the deeper structure, but defer for now. Simpler model first.
