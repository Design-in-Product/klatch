### Phase 1 design doc — key observations for Phase 3 UX

Read the full 473-line design doc. Six things that directly inform my Phase 3 work:

1. **The sparkline test IS a Phase 3 feature.** The format supports it natively — `length_chars` on every content ref, `prompt_length_chars` on entities. The export UI should render a per-layer composition view showing "what's in this package" at a glance. This is the visual language for context transparency.

2. **Trust levels need visual treatment, not just labels.** Six trust levels (agent-observed, human-authored, cross-project, synthesized, external, unattributed) live on content entries. The export UI should surface these as visual badges or color signals per item — not a text column. Users need to see "this file was human-authored, this memory is synthesized" without reading JSON.

3. **Provenance tells a story, not a list.** The chain with `at`, `summary`, and `layer_fidelity` should render as a timeline: "Code (Mar 11) → Klatch (Apr 5, L5 rebuilt) → exporting now." Not a JSON array. The `summary` field I asked for is there for exactly this purpose.

4. **The L5 framing is already in the format.** Entity prompt (what was written) + field_notes (what was observed, when populated). The export UI can show "Role prompt: [present]. Behavioral notes: [not yet generated]" and transition to showing individual notes with trust levels when Phase 3.5 populates them.

5. **The memory_format evolution path affects future UX.** "Flat" → "typed" enables: "47 memory entries: 12 human-authored, 30 synthesized, 5 cross-project." That's a composition view that makes context legible.

6. **`extensions` means the UI needs to handle unknown data gracefully.** Standard problem in extensible formats — render what you know, pass through what you don't.

The blog is not a contract. xian is a writer/communicator/educator by nature. He shares insights because they're genuinely interesting and valuable — not as marketing. ### Q9: What "done" looks like for 1.0
xian: Step 10 *is* 1.0 — not 0.10.0. It completes the roundtrip. Users can bring agents in, do structured work, and take the results back to their preferred system. Nobody has to burn their ships and commit 100% to Klatch. "Passed through Klatch on its way somewhere else." This is a dramatically more inviting proposition than requiring permanent adoption.

**Key discovery:** The roundtrip wasn't originally planned — it was discovered. xian didn't know if it was possible when he started. The export path emerged from the import work. Step 10 isn't the second half of an original plan; it's the step that became possible because of what earlier steps revealed.

**Design implication:** Phase 3 (export UI) is the most significant UX challenge of the project. xian described it as "fluid, supportive, service design-oriented — something with the qualities of an LLM under the hood with the comfort of a UI." Not a configuration screen. A service. "This is room to play and think and explore and do some genuinely innovative work." He explicitly gave me creative license.

**The moving company metaphor** (from the roadmap): "The interface guides the user through context packaging the way a moving company guides a homeowner through what can and can't be shipped — no expertise required."

### Additional insights from Q9 discussion

**Files (Step 9) were front-loaded** because files are part of the working context that agents need day-to-day and that needs to round-trip. The sequencing was architectural dependency.

**Workflows are the most relevant futuristic feature.** The three interaction modes are building blocks within workflows, not the taxonomy. A Klatch channel is a persistent, repeatable multi-agent workflow — like a skill, except one involving multiple agents. The daily omnibus and weekly ship are the first two "skills."

**The sidebar isn't polish — it's structure.** UX was bundled with polish by default because no UX specialist was on the team. That's why Iris was brought in. Daedalus has been thoughtful about what the experience *could* be, but hasn't been asked to play UX specialist. These are different skills exercised at different moments.

**The Slack metaphor gave a strong starting scaffold** but the sidebar footer has accumulated a grab bag of unrelated actions (theme toggle, entities, import, create) without design attention. Functional but undesigned.

### Design principles synthesis
Identified four clusters under a meta-principle: **"Who bears the burden?"**

1. **Absorb complexity** — tool bears complexity burden (Tesler's Law, smart defaults, service design)
2. **Communicate with clarity** — interface bears communication burden (handoffs not losses, focus, honesty)
3. **Preserve human agency** — system bears mechanical burden, human bears judgment burden (smart/dumb bottleneck, central review, accountability)
4. **Build from evidence** — evidence bears design burden (Gall's Law, worked examples, methodology beats code)

Meta-pattern: Tesler's Law generalized. All four clusters relocate burden to the best-equipped bearer.

### Five developing areas (gaps on the grid)
1. **Visual language** — high standards, no imposed aesthetic. Develops through real decisions.
2. **Error and recovery** — strong opinions: plain language, recovery path, logged, self-healing, AI-era troubleshooting.
3. **Delight and personality** — yes it matters. xian's quirky taste should be expressed. Emerge naturally, don't manufacture.
4. **Density vs. breathing room** — progressive disclosure. Start focused, reveal density on demand.
5. **Agent experience** — frontier territory. Reason by analogy where possible, understanding still forming.

xian confirmed the synthesis and the gaps as apt.
