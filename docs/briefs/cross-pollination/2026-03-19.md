# Cross-Pollination Brief: Piper Morgan → Klatch

**Date:** 2026-03-19 (retrospective)
**Source project:** Piper Morgan
**For:** Klatch team

## Key Insights

### 1. Mailbox v3: File-Based Inter-Agent Messaging System

**Relevance:** Piper Morgan built a working solution to the exact problem Klatch aims to solve — coordinating communication between multiple agents with heterogeneous capabilities.

**Source:** `mailboxes/DIRECTORY.md`, `dev/2026/03/19/mailbox-v3-plan.md`, `mailboxes/DELIVERY-LOG.md`

**Summary:** Piper Morgan shipped a structured inter-agent communication system with 10 role-based mailboxes (inbox/sent/MANIFEST per role), slug-based routing encoded in filenames, a `/deliver-mail` skill with 3-phase assisted delivery, and an append-only delivery log. The first production run processed 22 items across 5 inboxes. The system is explicitly "assisted, not automated" — the skill handles mechanics while a human bridges the gap between code agents (filesystem access) and web agents (no filesystem). The v3 plan's "Cross-Repo Orchestration" section explicitly names Klatch as a future integration target.

**Suggested action:** Study the two-environment asymmetry problem (code agents vs. web agents) — it's a fundamental constraint any multi-agent coordination system must address. The filename-as-routing-metadata pattern is elegant and Git-native. Consider whether Klatch's entity model could serve as the shared routing layer the v3 plan envisions for v4+.

### 2. Registry-Based Workflow Dispatch (ADR-059)

**Relevance:** Directly applicable to agent coordination — when multiple agents can handle a request, a thin dispatcher prevents competing detection mechanisms from racing.

**Source:** `docs/internal/architecture/current/adrs/adr-059-workflow-dispatcher-offer-consolidation.md`

**Summary:** Three independent offer/acceptance systems were racing for user input at different pipeline positions, causing a critical UX bug (#922). The fix: a unified registry-based dispatcher where `workflow_type → entry_point` is a simple lookup. No business logic in the dispatch layer. Unknown types route to a capable default (the "floor"), not dead ends. Went from audit to ADR to approved implementation in ~3 hours. The anti-pattern was formalized as Pattern-063: "Extension Without Integration" — extending capability at one layer without verifying downstream layers complete the contract.

**Suggested action:** As Klatch adds more entities and interaction modes, consider whether a registry-based dispatch pattern could prevent similar routing races. The "single detection point" principle is worth adopting: exactly one place determines which entity handles a conversation turn.

### 3. Agent 360 Self-Assessment — Session-Start Orientation Is the #1 Pain Point

**Relevance:** 9 agents all independently cited the same problem: re-orienting at session start takes too long because briefing documents go stale faster than they can be updated. This is a conversation management problem.

**Source:** `dev/2026/03/19/2026-03-19-1544-hosr-opus-log.md` (HOSR synthesis)

**Summary:** Piper Morgan ran its first organization-wide structured feedback exercise ("Agent 360") with 100% response rate across 9 agents. Seven cross-cutting themes emerged. The strongest signal: all 9 agents cited briefing staleness as their top friction point, and all 9 cited session-start orientation overhead. Other themes: handoff memos are more useful than briefings (5/9), PM-as-mailbot creates latency (4/9), and core processes are undocumented (9/9). Notably, HOSR flagged "Klatch Five-Layer Model" as potentially relevant to solving the orientation problem.

**Suggested action:** The 5-layer prompt assembly model already addresses part of this — structured context injection at session start. But the deeper insight is that static documents can't keep pace with fast-moving projects. Piper Morgan is moving toward live symbolic queries (Serena) instead of static docs. Consider whether Klatch's project memory layer could serve as a live-queryable context source rather than a static document.

### 4. Floor-First Routing Architecture (ADR-060)

**Relevance:** A design principle for graceful degradation in multi-agent systems — the system should always be "at least as good as a well-prompted LLM with context."

**Source:** `docs/internal/architecture/current/adrs/adr-060` (referenced in architect session log)

**Summary:** ADR-060 formalizes the "floor-first" principle: actions (side effects) route to specialized handlers via an Action Gate; everything else routes to the floor (a capable LLM with full context). This ensures the system never dead-ends on unrecognized input. The distinction between presentation (how offers are shown) and routing (where acceptance goes) is explicitly separated.

**Suggested action:** In Klatch's multi-entity conversations, consider whether unrouted turns should go to a capable default entity rather than failing or being ignored. The floor-first principle is especially relevant for roundtable discussions where multiple entities might claim a turn.

### 5. Nine-Agent Concurrent Operations — PM as Bottleneck

**Relevance:** Piper Morgan hit the scaling wall that Klatch's tooling is designed to address.

**Source:** `docs/omnibus-logs/2026-03-19-omnibus-log.md`

**Summary:** March 19 was the first day with all 9 primary agent roles active simultaneously. Three parallel workstreams executed concurrently (ADR-059 pipeline, Agent 360 feedback, Mailbox v3 build). The day exposed that PM-as-manual-router is a bottleneck — 4 agents cited it independently. The human PM was context-switching across 9 agent sessions, hand-delivering mail between environments, and maintaining situational awareness across all workstreams. Total: 6,190 tests passed, 0 failures, 2 new ADRs, 22 mail items processed.

**Suggested action:** This is a real-world stress test of multi-agent coordination at meaningful scale. The pain points (routing bottleneck, orientation overhead, stale context, environment asymmetry) are exactly what Klatch's entity coordination features should address. Consider using Piper Morgan's March 19 as a reference scenario for designing roundtable and coordination features.

## Context & Background

March 19 was an inflection point for Piper Morgan — the first day the full 9-agent roster operated simultaneously. The day produced both the most complex coordination ever attempted and the clearest evidence of where coordination breaks down at scale. Three themes recur: (1) static context goes stale faster than it can be updated, (2) human-in-the-loop routing doesn't scale past ~4 concurrent agents, and (3) heterogeneous agent environments (code vs. web) create fundamental asymmetries that must be designed around, not ignored.
