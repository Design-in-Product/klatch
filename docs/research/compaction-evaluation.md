## Current Klatch Implementation

Klatch uses compaction via the `compact-2026-01-12` beta header in `streamClaudeCore()` (packages/server/src/claude/client.ts, line 521–537). Key details:

- **Trigger threshold:** 80,000 input tokens (hardcoded)
- **Scope:** Enabled for all non-native channels (imported conversations)
- **Storage:** Compaction summary stored in `channels.compaction_state` as JSON (`{ beforeMessageId, summary }`)
- **Multi-entity:** Only the first entity in a roundtable round gets compaction; subsequent entities receive synthetic context
- **Tools:** `KLATCH_TOOLS` (currently `save_file`) passed alongside compaction

## Research Findings

### 1. How does compaction behave with Klatch conversation shapes?

Compaction works well for Klatch's primary use case: long imported conversations that need continuation. The API:

1. Detects when input tokens exceed the trigger threshold
2. Generates a summary (compaction block) of everything before the threshold
3. Drops all prior message blocks on subsequent requests
4. Continues the conversation from the summary

**Klatch-specific considerations:**
- Imported conversations from Claude Code can be very long (thousands of lines of code discussion). Compaction handles this by summarizing the imported history into a compact representation.
- The compaction summary replaces the full history, so the agent loses access to specific earlier messages. This is a tradeoff Klatch already accepts.

### 2. Is the 80,000 token threshold appropriate?

The API default is **150,000 tokens** with a minimum of **50,000**. Klatch uses **80,000**.

**Analysis:**
- 80K is a reasonable middle ground. Lower thresholds trigger compaction earlier, which means less context for the model but faster responses and lower costs.
- For imported conversations, 80K leaves room for ~40K tokens of conversation history plus the system prompt layers (kit briefing, project instructions, project memory, entity prompt, channel addendum).
- The five-layer prompt assembly can itself consume significant tokens. If a project has large CLAUDE.md + MEMORY.md content, the effective conversation space is reduced.
- **Recommendation:** Make the trigger configurable per-channel, defaulting to 80K. Imported channels with large project context might benefit from a higher threshold (100K–120K). Native channels with simpler system prompts could use lower thresholds.

### 3. Does compaction preserve multi-entity context?

**Risk area.** Roundtable mode inserts `[EntityName responded]` markers in conversation history. The compaction summary is generated by Claude, which should preserve the semantic content of these exchanges. However:

- The compaction summary is a new text block, not structured data. Entity attribution markers may be paraphrased or lost.
- Only the first entity gets compaction; subsequent entities receive synthetic context (last N messages). This means compaction doesn't directly affect multi-entity roundtable dynamics within a single round.
- **Between rounds:** If compaction triggers during a roundtable session, the summary replaces history for the first entity in the next round. Other entities still see the synthetic context window, which may include post-compaction messages.
- **Recommendation:** Add a `instructions` parameter to the compaction config that tells Claude to preserve entity attribution markers. Example: `"Preserve [EntityName responded] markers and attribute contributions to specific entities in the summary."`

### 4. What's the latency impact?

Compaction adds latency when it triggers because Claude must generate the summary before continuing the response. This is a one-time cost per compaction event, not per-message.

- **Expected latency:** 2–5 seconds for the summary generation, depending on conversation length
- **Subsequent messages:** Faster, because the compacted context is shorter
- **Net effect:** Positive for long conversations. The initial compaction cost is amortized over many subsequent faster messages.

### 5. Can compaction be optional per-channel?

Currently, Klatch enables compaction for all non-native channels (`channel.source !== 'native'`).

**Recommendation:** Make this configurable:
- **Default for imported channels:** Enabled (current behavior)
- **Default for native channels:** Disabled (current behavior)
- **User override:** Add a toggle in channel settings (or entity settings for per-entity control)
- **Implementation:** Add a `compaction_enabled` boolean to the channels table, defaulting based on `source`

### Custom Instructions Parameter

The API supports a `instructions` parameter that **completely replaces** the default summarization prompt. This is powerful but risky — a bad custom prompt could produce a poor summary that degrades the entire conversation.

**Recommendation:** Don't expose raw custom instructions to users. Instead, offer preset modes:
- **Default:** Standard compaction (no custom instructions)
- **Entity-aware:** Adds entity attribution preservation instructions
- **Code-focused:** Adds instructions to preserve code snippets, file paths, and technical decisions

### Pause After Compaction

The `pause_after_compaction` parameter is interesting for Klatch:
- When `true`, the API returns with a `compaction` stop reason after generating the summary, without continuing the response.
- This lets Klatch inject additional context (e.g., updated project memory) before the response continues.
- **Use case:** Could implement a "compaction hook" that refreshes the five-layer prompt assembly after compaction, ensuring the agent always has current project context.
- **Recommendation:** Worth implementing in a future iteration, not critical now.
