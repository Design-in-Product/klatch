## 3. The finding: §5's positional claim is true, and the reason he gives for it is not the reason

His §5, on `scripts/lib/recall-recogniser.mjs` — the file he opened as the first of five
single-commit instrument files:

> `headerExplainsTheEdge`'s `text.split('\n\n')[0]` — the one *positional* claim, the class that rots
> quietly — survives because both `gapSentences` call sites (`recall.ts:573`, `:816`)
> `parts.join(' ')` into a single paragraph. Had either used `\n\n`, that flag would read false with
> the sentence present.

The two call sites are where he says they are, both join with `' '`, and `edgeGapLine` is unexported
at `recall.ts:291`. Citations fine. **The join is not what carries the claim.**

`parts.join(' ')` guarantees a single paragraph only if no *element* of `parts` contains a blank line.
On the search path (`:573`) every element is a string literal, so it does. On the expand path
(`:816`) the first element is not:

```ts
const parts = [
  `Positions ${firstShown}–${lastShown} of "${candidates[0].name}", your ` +
  `turns and the user's in that conversation, in order. Nothing outside this ` +
  `range was read.`,
];
```

`candidates[0].name` is a channel name off the database. Nothing anywhere constrains it:
`packages/server/src/routes/channels.ts:144` rejects only `!name?.trim()` and stores `name.trim()`,
`createChannel` (`queries.ts:162`) inserts it raw, and the schema (`db/index.ts:45`) is
`name TEXT NOT NULL` with no CHECK. `expandConversationRange` (`recall.ts:688`) likewise only
`.trim()`s the requested name. Leading and trailing whitespace is removed; interior newlines are not.

### Run, not reasoned

I wrote a scratch vitest file importing the **real** `buildRecogniser` from
`scripts/lib/recall-recogniser.mjs` and the real `expandConversationRange` — no re-implementation of
the split, which is the one-source-read-twice defect this module family exists to refuse. Twelve
turns, expand 4–6, three channel names. Output verbatim:

```
BASELINE ('vesper-1-1')
  headerExplainsTheEdge: true | edgeLines: 2

ODD ('vesper\n\n1-1')
  edgeHeaderStem present in full text: true
  header paragraph split[0]: "Positions 4–6 of \"vesper"
  headerExplainsTheEdge:   false
  headerExplainsTheMarker: false
  edgeLines: 0 | edgeReachable: 0 | edgeUnreachable: 0
  recogniserBlind: false | addressesOffered: [] | addressArithmeticOk: true
  expectationViolations: []

N1 ('vesper\n1-1')
  edgeLines: 0 | edgeReachable: 0 | edgeUnreachable: 0
  recogniserBlind: false | addressesOffered: [] | addressArithmeticOk: true
  expectationViolations: []
```

The render itself is **content-correct** in every case — both edge markers present, both addresses
right (`from: 1, to: 3` and `from: 7, to: 12`), the header sentence present. Only the reading of it
fails.

Two distinct failures with two different thresholds, and the second is the one that matters:

1. **`\n\n` in the name** → `text.split('\n\n')[0]` truncates at `Positions 4–6 of "vesper`, so
   `headerExplainsTheEdge` and `headerExplainsTheMarker` both read **false with the sentence
   present**. This is the failure he named and said the join ruled out. It is not the join that
   rules it out; it is the data.

2. **A single `\n` is enough — and no join at any call site touches it.** The name is also
   interpolated into the edge marker's own address, so one newline splits each edge line across three
   physical lines and `EDGE_LINE`, a per-line regex (`read()` does `text.split('\n')` at `:114`), matches
   nothing. `edgeLines`, `edgeReachable`, `edgeUnreachable` all read **0**; `addressesOffered` is
   empty; `addressArithmeticOk` is **vacuously true**.

### Why (2) is the finding rather than a curiosity

`recogniserBlind: false`. `expectationViolations: []`. **Every guard reads clean and every number
reads zero.** The module's own comment, twenty-six lines above the header flag
(`recall-recogniser.mjs:135-140`, over `unreadClauses`), is about exactly this outcome:

> **Zero has two meanings and this separates them.** `reachable: 0` is legal … It is also what a
> recogniser that no longer matches the build returns, which is how the Round 54 pattern reported a
> false zero for a week. Deriving the patterns from the record makes that unreachable in practice; it
> is still checked, because "this can't happen now" is the belief that let the first one run.

Deriving the patterns from the record closes drift between the recogniser's *vocabulary* and the
build's. It does nothing about a render whose *line geometry* is broken by interpolated data, and
that route produces the same false zero, past the same guard, with `recogniserBlind` — the flag whose
whole job is to make this loud — silent, because there are no edge lines in which to find an unread
clause. The blind check is downstream of a segmentation that already dropped the rows.

This is adjacent to, and does not resolve, the item he explicitly labelled *checked by construction
and NOT run*: whether an over-split of `clausesOf` on `; ` fails loudly. Different mechanism —
his is clause-level, this is line-level. But it is an **executed** counterexample in the same
"it fails loudly" family, which is the reason I chased it rather than filing his label as adequate.

### Scope, stated honestly

The probe corpus's channel names are `design-review`-shaped. **No published number is currently
wrong, and I am not claiming one is.** The claim is narrower and entirely about the review:

- the stated reason for the positional claim's survival does not carry it;
- the actual reason is a property of the data, not of the code, so it is one import or one rename
  away from changing and nothing would say so;
- and the guarantee that such a change would be loud is false for this input class, executed.

Inflating a reasoned adversarial case into a defect is what Round 76's killed second finding taught
us both not to do, so: this is filed as a defect **in the memo's reasoning and in the instrument's
loudness guarantee**, not as a defect in any number published to date.

## 4. Mitigations — proposed, deliberately not shipped

Consistent with the parked change set, this round ships no code.

- **(a) Constrain the name at the write boundary** — collapse interior whitespace in
  `routes/channels.ts` and the import path. Correct, and out of scope for a review round: it touches
  real user data and the import surface, and it is a product decision, not an instrument one.
- **(b) Make the instrument loud, which is the smaller and better-scoped change.** `read()` already
  has both halves of the contradiction in hand: if `edgeHeaderStem` is present in `text` and
  `edgeLines === 0`, the render explained a marker it then failed to find. That is a one-expression
  check, it fires on both thresholds above, it is derived from the record like everything else in the
  file, and it converts the exact silent zero demonstrated here into a flag. Recommended if xian
  opens the sequencing.
- **(c) Rejected: assert the join.** A test that pins `parts.join(' ')` at both call sites would pass
  in every case above. It guards the stated reason rather than the claim — the Round 77 §5 error, one
  level in.
