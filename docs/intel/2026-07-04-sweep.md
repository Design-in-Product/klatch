### 6. PM Engineering Pattern: Atomic Token Burn + Completeness Guard (July 3)

Cross-pollination brief (7/4) carried two engineering patterns from PM's July 3 session:

**Atomic token burn (invite-gate):** When PM added invite-code gating to user creation, the critical constraint was that the token validation and account creation must be atomic — a conditional UPDATE + INSERT in the same transaction. A TOCTOU race otherwise allows two concurrent requests to both pass validation. The empirical test: `asyncio.gather` two concurrent `create_user` calls at a real DB with the same token; assert exactly one succeeds. A mock can't catch this class of race.

**Completeness guard:** PM landed a `test_every_degradation_reason_has_nudge_copy` test in the same commit as a new enum member, ensuring that future enum extensions fail immediately if they omit the parallel data entry.

Klatch impact: The atomic-burn pattern is relevant if Klatch ever adds multi-user invite flows. The completeness guard pattern is immediately applicable: Klatch has `AVAILABLE_MODELS` (and potentially `INTERACTION_MODES`) as growing registries where a new entry might be added without a corresponding label/description. Worth filing as a hardening candidate for Daedalus.

**Source:** Cross-pollination brief 2026-07-04 (`docs/briefs/cross-pollination/2026-07-04.md`)  
**Klatch impact:** Medium. The completeness guard pattern applies to `AVAILABLE_MODELS` — if a model is added to the API but not to AVAILABLE_MODELS, the UI silently omits it (which is intentional) but a test that asserts the overlay is exhaustive would make the gap visible. Route to Daedalus as a low-priority hardening item.  
**Prior mentions:** None. Cross-project pattern find.  
**Verified against:** `packages/shared/src/types.ts:AVAILABLE_MODELS` — no completeness test exists today for this registry.
